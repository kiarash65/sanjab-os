# سیاست انتشار SanjabOS — مبنا: نسخهٔ ۴٫۰٫۰

این سند سیاست انتشار را برای مخزن فعلی تعریف می‌کند. انتشار تازه تا عبور از دروازه‌های فنی، محتوایی، امنیتی و نصب واقعی **نامزد انتشار** باقی می‌ماند؛ سبزشدن build به‌تنهایی به معنی آماده‌بودن محصول برای کاربر نهایی نیست.

## ۱. منبع نسخه و SemVer

- تنها منبع نسخهٔ وب و CLI فایل VERSION در ریشهٔ مخزن است؛ نسخهٔ package.json و src-tauri/tauri.conf.json باید با آن برابر باشند.
- قالب MAJOR.MINOR.PATCH است؛ تگ انتشار دقیقاً v<VERSION> خواهد بود.
- **MAJOR:** تغییر ناسازگار در قرارداد داده، فایل‌سیستم، ذخیره‌سازی یا API.
- **MINOR:** قابلیت تازه با سازگاری عقب‌رو.
- **PATCH:** اصلاح امنیتی/اشکال بدون تغییر قرارداد داده.
- پیش از تکمیل ماتریس آزمون و ثبت تصمیم انتشار، VERSION یا تگ را جلو نبرید.

## ۲. تعریف وضعیت قابلیت‌ها

هر قابلیت باید یکی از وضعیت‌های زیر را با شواهد مشخص اعلام کند:

| وضعیت | معنای دقیق |
|---|---|
| واقعی در مرورگر | کد/محاسبه در محیط مرورگر واقعاً اجرا می‌شود؛ محدودیت مرورگر همچنان پابرجاست |
| runtime واقعیِ جداشده | مفسر/سیستم‌عامل واقعی در Worker، WASM یا ماشین مجازی اجرا می‌شود |
| شبیه‌ساز آموزشی | فقط زیرمجموعه‌ای از رفتار را مدل می‌کند؛ نباید با runtime کامل اشتباه شود |
| نیازمند پل بومی | فقط با نصب/اجازهٔ کاربر و پل دسکتاپ قابل اجراست |
| برنامه‌ریزی‌شده | در نسخهٔ فعلی تحویل نشده؛ نباید در متن بازاریابی «موجود» معرفی شود |

محدودیت امنیتی، حریم خصوصی، زمان اجرا، اندازهٔ ورودی یا rate limit را برای تبلیغ «بدون محدودیت» حذف نکنید. هر سقف باید دلیل، مقدار، پیام UI و مسیر امن افزایش/تنظیم داشته باشد.

## ۳. گیت‌های اجباری انتشار

### کیفیت کد و محتوا
1. نصب وابستگی‌ها با lockfile ثابت و نسخه‌های پین‌شده.
2. typecheck سخت‌گیرانه، ESLint، آزمون‌های رگرسیون محتوا/API و build standalone.
3. آزمون همگامی شناسه‌های آکادمی و رجیستری مرکز یادگیری.
4. آزمون مسیرهای اصلی در مرورگر دسکتاپ و موبایل؛ شامل keyboard-only و reduced-motion.
5. بازبینی محتوا و فارسی با گزارش منبع/درس/ادعا و نتیجهٔ اصلاح.

### Runtime و نصب واقعی
1. Pyodide: اجرای تمرین واقعی، timeout، سقف خروجی، قطع Worker و رفتار آفلاین/CDN.
2. Linux v86: بوت واقعی Alpine، شبکه، snapshot/restore، مصرف حافظه و توقف clean.
3. Rust: مشخص‌کردن دقیق تفاوت شبیه‌ساز با rustc؛ تست پل Native فقط با opt-in و مرز امنیتی روشن.
4. PowerShell: مشخص‌کردن تفاوت شبیه‌ساز خط لوله با PowerShell 7/Windows PowerShell؛ هیچ فرمانی نباید وانمود کند روی میزبان اجرا شده است.
5. Windows Tauri: نصب تمیز NSIS و MSI، اجرا، خاموشی پردازهٔ sidecar، حذف، ارتقا و rollback.
6. Linux edition: boot/install smoke test واقعی برای هر بسته‌ای که قرار است منتشر شود؛ تا پیش از آن وضعیت «آزمایش‌نشده» باقی بماند.
7. اگر macOS یا Android رسماً پشتیبانی نمی‌شوند، آن‌ها را در ماتریس پشتیبانی «آزمایش‌نشده/پشتیبانی‌نشده» ثبت کنید، نه اینکه سکوتاً ادعا کنید.

### زنجیرهٔ انتشار و فایل‌ها
- نسخهٔ VERSION، package.json، Tauri، Debian/Arch package metadata و تگ Git باید دقیقاً هم‌خوان باشند.
- گیت انتشار باید typecheck، lint، regression tests و build را اجرا کند.
- فایل‌های نهایی باید شامل SBOM، Third-party Notices، نسخه، release notes و SHA256SUMS.txt باشند.
- checksum را پس از اضافه‌شدن تمام assetها دوباره تولید کنید؛ خود checksum نیز باید از مسیر release قابل دریافت باشد.
- برای هر asset، معماری، سیستم‌عامل، نوع نصب، حجم، امضای دیجیتال (در صورت فراهم‌بودن) و وضعیت آزمون ثبت شود.
- شکست یک پلتفرم نباید بی‌صدا پنهان شود. انتشار وب-only فقط با یادداشت صریح و تصمیم release owner مجاز است.

## ۴. فرآیند پیشنهادی

1. همهٔ تغییرات روی branch نامزد انتشار و سپس merge کنترل‌شده به main.
2. اجرای CI کامل و ذخیرهٔ لینک run.
3. ساخت RC بدون انتشار پایدار؛ نصب و تست واقعی روی دستگاه/ماشین مجازی.
4. بستن P0های امنیتی، از دست‌رفتن داده، نصب/به‌روزرسانی و خطاهای آموزشی.
5. ثبت Known limitations با وضعیت واقعی هر runtime.
6. تصمیم صریح owner؛ سپس bump نسخه، changelog، هم‌ترازی package metadata و تگ.
7. انتشار artifactها و کنترل دانلود/checksum پس از انتشار.
8. نگه‌داری نسخهٔ قبلی و مسیر rollback؛ هیچ migration مخربی بدون backup و آزمون restore.

## ۵. سیاست داده و امنیت

- هر migration باید قبل از تغییر، backup قابل‌بازیابی بگیرد و بعد از restore آزمایش شود.
- هیچ به‌روزرسانی نباید از git reset --hard یا حذف دادهٔ کاربر استفاده کند.
- کلیدهای API، پسوردها و داده‌های خصوصی نباید وارد backup، log، analytics یا prompt گزارش شوند.
- timeout، محدودیت حجم ورودی/خروجی، rate limit، allowlist فرمان و جداسازی Worker/VM گیت امنیتی‌اند؛ حذف آن‌ها «کاهش محدودیت محصول» محسوب نمی‌شود.
- اجرای فرمان native، دسترسی فایل یا شبکه باید opt-in، با scope روشن و قابل لغو باشد.
