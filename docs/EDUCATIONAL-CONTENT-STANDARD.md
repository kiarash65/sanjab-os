# استاندارد محتوای آموزشی سنجاب‌اواس

> نسخه ۱٫۰ — قرارداد ساخت درس برای همهٔ آکادمی‌ها. هر توسعه‌دهنده یا ایجنتی که درس جدیدی اضافه می‌کند باید این سند را اجرا کند.
> مخاطب مرجع: دانش‌آموز ۱۶ سالهٔ باهوش، آشنا به کامپیوتر، بدون پیش‌زمینهٔ برنامه‌نویسی.

---

## ۱. الگوی ۱۳‌بخشی درس

هر درس باید دانش‌آموز را از نقطهٔ ناآشنایی به فهم واقعی برساند. اجرای مکانیکی و پرکردن صفحه هدف نیست؛ انتقال واقعی دانش هدف است. بر اساس ماهیت موضوع، وزن بخش‌ها می‌تواند متفاوت باشد، اما حداقل آموزش لازم برای فهم کامل باید حضور داشته باشد.

| # | بخش | الزام |
|---|---|---|
| ۱ | **پیش‌نیاز** | صریح بنویس چه چیزی لازم است؛ اگر هیچ‌چیز، صریحاً «هیچ پیش‌نیازی ندارد». اتکای درس به درس قبلی مشخص شود. |
| ۲ | **هدف درس** | قابل‌آزمایش، نه «آشنایی با...». خوب: «در پایان این درس می‌توانی یک متغیر بسازی، مقدارش را تغییر بدهی و در خروجی نمایش بدهی.» |
| ۳ | **مسئلهٔ شروع** | با پرسش یا مسئلهٔ ملموس شروع کن («اسم و سن‌ات را چطور به برنامه بدهیم؟»)، نه با تعریف فرهنگ‌لغتی. |
| ۴ | **تعریف ساده** | فارسی روزمرهٔ دقیق. هر اصطلاحِ استفاده‌شده یا قبلاً تدریس شده یا همین‌جا تعریف می‌شود. |
| ۵ | **چرا لازم است؟** | کاربرد واقعی؛ دانش‌آموز باید بداند چرا متغیر/حلقه/مالکیت وجود دارد. |
| ۶ | **مثال ملموس** | از دنیای آشنا: بازی، مدرسه، نمره، فایل‌ها، موسیقی، فهرست کارها. کودکانه و ساختگی نه. |
| ۷ | **مرز تشبیه** | بعد از تشبیه بگو در دنیای واقعی دقیقاً به چه اشاره می‌کند و کجا دیگر جواب نمی‌دهد؛ هیچ تشبیهی نباید برداشت اشتباه از عملکرد زبان بسازد. |
| ۸ | **مثال عملی مرحله‌به‌مرحله** | کد + کار هر خط + چرا لازم است + ترتیب اجرا + خروجی واقعی + «اگر این خط تغییر کند چه می‌شود؟» |
| ۹ | **اشتباه‌های رایج** | چرا مبتدی این خطا را می‌کند، چه اتفاقی می‌افتد، پیام خطا چه معنایی دارد، چطور اصلاح می‌شود. |
| ۱۰ | **تمرین هدایت‌شده** | مشابه مثال درس، با سرنخ‌های چندمرحله‌ای (حداقل ۲ سرنخ) و راه‌حل توضیح‌داده‌شده. جواب نهایی بلافاصله داده نشود. |
| ۱۱ | **تمرین مستقل** | کمی متفاوت از مثال، تا فهم واقعی سنجیده شود. |
| ۱۲ | **راهنمای مرحله‌ای** | سرنخ ۱ → سرنخ ۲ → راه‌حل کامل → تحلیل راه‌حل. |
| ۱۳ | **خلاصه و خودارزیابی** | ۳–۵ نکتهٔ اصلی + چند پرسش سنجش فهم + یک کار کوچک مستقل. |

**قاعدهٔ طلایی مفاهیم:** هیچ مفهومی فقط با یک جمله معرفی و بلافاصله در تمرین پیشرفته استفاده نمی‌شود. هیچ مثالی از مفهومی استفاده نمی‌کند که هنوز تدریس نشده (مثلاً درس اول پایتون نباید if/else نشان بدهد).

## ۲. نگاشت به اسکیمای داده

درس‌های موجود سه شکل متفاوت دارند (Python غنی، PowerShell ساده، Rust پاراگرافی). برای یکدست‌شدن، این فیلدهای اختیاری مشترک به همهٔ آکادمی‌ها اضافه می‌شود. فیلدهای اختیاری‌اند تا پیشرفت و شناسهٔ درس‌ها و کلیدهای ذخیره‌سازی کاربران دست‌نخورده بماند:

```ts
interface LessonExtra {
  goal?: string[]            // هدف‌های قابل‌آزمایش (بخش ۲)
  problem?: string           // مسئلهٔ شروع (بخش ۳)
  whyMatters?: string        // چرا این مفهوم لازم است (بخش ۵)
  analogyLimit?: string      // مرز تشبیه: کجا دیگر جواب نمی‌دهد (بخش ۷)
  guidedExercise?: {         // تمرین هدایت‌شده (بخش‌های ۱۰ و ۱۲)
    task: string
    hints: string[]          // سرنخ ۱، سرنخ ۲، ...
    solution: string         // راه‌حل کامل
    solutionExplain: string  // تحلیل راه‌حل
  }
  selfCheck?: {              // خلاصه و خودارزیابی (بخش ۱۳)
    points: string[]         // ۳–۵ نکتهٔ اصلی
    questions: string[]      // پرسش‌های سنجش فهم
    task: string             // یک کار کوچک مستقل
  }
}
```

- در پایتون: فیلدها به `PyLesson` اضافه می‌شود (کنار `intro/analogy/technical/...` موجود).
- در پاورشل و Rust: ساختار فعلی حفظ و همین فیلدهای اختیاری به‌کار می‌رود؛ رندرکننده بخش‌های موجود را دارا و بخش‌های جدید را اختیاری نمایش می‌دهد.
- بخش Output خروجی کد در هر آکادمی باید نمایش داده شود (یا داخل توضیح مثال، یا به‌صورت بلوک مجزا).
- **شناسهٔ درس‌ها (`id`) و کلیدهای پیشرفت هرگز تغییر نمی‌کنند** — پیشرفت کاربران باید حفظ شود.

## ۳. صداقت شبیه‌ساز

- هر آکادمی باید صادقانه بگوید چه چیزی واقعی اجرا می‌شود و چه چیزی شبیه‌سازی است:
  - پایتون: اجرای واقعی CPython از طریق Pyodide — با محدودیت‌های واقعی (پکیج‌های محدود، بدون شبکه، بدون فایل واقعی).
  - پاورشل: شبیه‌ساز آموزشی — نه PowerShell واقعی ویندوز کاربر. دستورهای مخرب فقط به‌صورت تمرین ایمن و غیرمخرب.
  - Rust: Memory Lab شبیه‌سازی مفهومی است؛ خطای نمایش‌داده‌شده را خطای واقعی rustc معرفی نکن.
- مثال‌ها نباید وانمود کنند روی سیستم واقعی کاربر عملیاتی انجام می‌دهند.
- ادعاهای فنی با مستندات رسمی کنترل می‌شود: docs.python.org، learn.microsoft.com/powershell، doc.rust-lang.org/book.

## ۴. چک‌لیست کیفیت هر درس (Rubric)

پیش از تحویل، هر درس باید همهٔ موارد زیر را پاس کند:

- [ ] مبتدی پیش‌نیاز لازم را دارد (یا درس صریحاً بی‌پیش‌نیاز است)
- [ ] هیچ مفهوم جدیدی قبل از معرفی استفاده نشده
- [ ] تعریف با زبان ساده و صحیح ارائه شده
- [ ] مثال برای مخاطب ۱۶ ساله قابل‌فهم است
- [ ] خروجی کد نمایش داده شده و با اجرای واقعی سازگار است
- [ ] بخش‌های مهم کد خط‌به‌خط توضیح داده شده‌اند
- [ ] خطاهای رایج با علت و راه اصلاح تشریح شده‌اند
- [ ] تمرین از سطح درس فراتر نرفته
- [ ] راهنمای مرحله‌ای (سرنخ‌ها) وجود دارد
- [ ] آزمونک واقعاً فهم مفهوم را می‌سنجد، نه حفظ عبارت
- [ ] گزینه‌های نادرست آزمونک توضیح دارند (چرا غلط‌اند)
- [ ] فارسی طبیعی است (بدون کلیشه‌های راهنمای نگارش)
- [ ] اصطلاحات با واژه‌نامهٔ مشترک یکدست‌اند
- [ ] ادعاهای فنی درست‌اند و با رفتار شبیه‌ساز/رuntimes واقعی سازگارند
- [ ] شناسهٔ درس و کلیدهای پیشرفت تغییر نکرده‌اند

## ۵. آزمون فهم مبتدی

- برای هر درس، چند پرسش طراحی کن که دانش‌آموز فقط اگر توضیحات را فهمیده باشد بتواند پاسخ دهد (نه حدس و نه جست‌وجوی بیرونی).
- بازبینی مستقل: یک ایجنت با نقش «دانش‌آموز ۱۶ سالهٔ بدون سابقه» متن را می‌خواند و موارد زیر را علامت می‌زند:
  1. اصطلاحات نامفهوم
  2. پرش‌های مفهومی (مرحله‌ای که بدون حدس عبور نمی‌شود)
  3. مثال‌های ناقص یا بدون خروجی
  4. جاهایی که بعد از خواندن هنوز معلوم نیست چه‌کار باید کرد
- اگر برای فهم یک درس حدس‌زدن یا جست‌وجوی بیرونی لازم است، درس آماده نیست.
- این شبیه‌سازی ارزیابی است، نه تست واقعی دانش‌آموز؛ در گزارش‌ها صادقانه «بازبینی شبیه‌سازی‌شده» نامیده می‌شود.
